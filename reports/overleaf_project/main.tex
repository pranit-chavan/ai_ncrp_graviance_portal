\clearpage\chapter*{Abstract}\addcontentsline{toc}{chapter}{Abstract}

People reporting online fraud often need to describe an incident, identify payment details, preserve evidence, and explain what happened to an investigator. This project provides a local web application that guides a complainant through a conversational or manual intake, accepts typed text, speech transcripts, and evidence files, and prepares a structured complaint draft. A separate investigator environment stores submitted case records in a local inbox for review.\par\medskip
The current implementation combines a FastAPI service with a standalone HTML, CSS, and JavaScript interface. The earlier Streamlit dashboard remains in the repository. Complaint text can be classified into a 21-label taxonomy using a saved TF-IDF and LinearSVC model. OCR uses Tesseract, with PDF/image handling and deterministic pattern extraction for fields such as amounts, transaction references, UPI IDs, dates, times, bank names, payment apps, and masked account details. Extracted evidence is shown alongside the complainant's account; agreement, evidence-only values, missing fields, and conflicts are represented separately so that uncertain evidence is not silently treated as confirmed fact. A conversational assistant asks follow-up questions, while a manual form and editing controls provide an alternative. Speech capture/transcription is available through browser speech recognition and optional local Whisper processing, depending on the selected path and installed dependencies.\par\medskip
After confirmation, the application can create a structured case record and draft PDF. The investigator interface supports a local review queue, case detail review, evidence inspection, workflow updates, and JSON case import. Local SQLite databases persist intake sessions and indexing/workflow information; case JSON and evidence files are stored separately in local folders. Legal references and urgency indicators are suggestions for review, not decisions.\par\medskip
The project is a functional academic prototype, not an official reporting service or production case-management platform. The included classification data are generated and intentionally vocabulary-separated; the repository itself warns that excellent benchmark scores on these splits do not measure real-world accuracy. Human verification, privacy safeguards, access control, independent evaluation, and operational deployment remain essential future work.\par\medskip
\textbf{Keywords:} cybercrime intake, complaint drafting, text classification, OCR, evidence reconciliation, speech transcription, investigator review, human oversight.\par\medskip

\clearpage\chapter{Introduction}
\section{Background}
Cybercrime complaints can contain several kinds of information in different forms: a person's narrative, a payment notification, a bank message, a chat screenshot, a voice description, or a transaction identifier. A complainant may not know which details are useful, and investigators need to review the narrative and supporting evidence together. Repeatedly asking for details already visible in an uploaded receipt creates friction and may lead to inconsistent records.\par\medskip
This project addresses the information-collection and organization stage. It combines a guided intake with file-based evidence extraction and a separate investigator review experience. Its purpose is to help a person prepare a more complete, editable draft and to make the captured information easier to inspect. It is not a replacement for official channels or investigator judgment.\par\medskip
\section{Project evolution}
The Phase I report described a proposed NLP-based cybercrime complaint classifier. The current repository has grown into a broader local prototype: it includes a citizen-facing web interface, conversational and manual intake, OCR-based evidence extraction, voice input/transcription paths, case drafting and persistence, and an investigator queue. The report therefore documents the implementation found in the repository, rather than presenting Phase I proposals as completed work.\par\medskip
The system currently has two interface paths. FastAPI serves a separate static frontend from \texttt{static/}; \texttt{dashboard.py} retains the Streamlit application. These frontends share domain modules and service functionality, but they are distinct user interfaces and may not expose precisely identical interactions. The investigator workflow is part of the newer web interface and should be validated independently from the Streamlit view.\par\medskip
\section{Objectives}
\begin{itemize}
\item Provide an accessible intake path using conversation, a manual form, typed input, and speech-derived text.
\item Collect key facts and ask targeted follow-up questions where information remains missing.
\item Let a complainant upload evidence and review OCR-derived fields before using them in a draft.
\item Identify a likely complaint category as decision support and display uncertainty and alternatives.
\item Produce a structured, editable complaint draft and a downloadable document.
\item Store submitted records in a local investigator review workflow, with evidence associated with its individual case.
\item Keep the process understandable to non-technical users and preserve human review at important decision points.
\end{itemize}
\section{Intended users}
\textbf{Complainant:} describes an incident, uploads evidence, reviews extracted details, corrects the draft, and chooses to submit the local case record.\par\medskip
\textbf{Investigator or reviewer:} opens records received in the local inbox, checks the narrative and evidence, reviews extraction conflicts and model suggestions, and updates the case workflow.\par\medskip
The terms ``complainant'' and ``investigator'' refer to prototype roles and do not imply authenticated real-world identities or official jurisdictional authority.\par\medskip
\clearpage\chapter{Literature Survey}
\section{Text classification}
TF-IDF represents text using weighted terms and is a common baseline for document categorization. Linear support-vector classification provides an efficient linear decision boundary and supports multiclass classification through a one-versus-rest approach in scikit-learn. This combination is useful as a lightweight, inspectable baseline for categorizing complaint narratives. It does not by itself establish semantic understanding, calibrated probabilities, or operational suitability. The implementation uses the highest decision margin and a bounded transformation of the gap between top margins as a confidence-like score; this number is a heuristic and must not be interpreted as a calibrated probability.\par\medskip
Joulin et al. describe efficient text classification with bag-of-words and n-gram features as a practical baseline [1]. The current project uses a TF-IDF + LinearSVC implementation rather than fastText, but the reference supports the broader use of sparse lexical representations as baselines.\par\medskip
\section{Optical character recognition}
OCR converts image pixels into text that can be searched and processed. The project uses Tesseract through \texttt{pytesseract}, then applies deterministic patterns and known-name matching to extract candidate entities. This approach is auditable and avoids asking a generative model to invent exact transaction identifiers. OCR remains sensitive to image quality, fonts, cropping, contrast, transliteration, and character confusion. A recognized value must therefore retain provenance and be checked against the original attachment.\par\medskip
\section{Speech recognition}
Automatic speech recognition produces text from audio and can make intake more accessible. The repository supports browser speech recognition for live capture in supported browsers and optional local Whisper transcription for uploaded audio when its package and model dependencies are available. Radford et al. describe Whisper's multilingual weakly supervised training and its robustness across several speech tasks [2]. Recognition errors are still possible, especially with noise, accents, code-switching, names, and numeric identifiers. The user must be able to inspect and correct transcripts before relying on them.\par\medskip
\section{Conversational intake and human-centered automation}
A conversational interface can guide a person through details that are easy to omit. For reliable data collection, questions should be tied to explicit information gaps, responses should update a visible draft, and previously answered fields should not be repeatedly requested. The current implementation combines LLM-backed behavior with deterministic state and fallback logic. Provider availability and response quality depend on configuration, and every generated question or narrative needs validation. This project therefore treats the assistant as a drafting aid, not an authoritative source.\par\medskip
\section{Evidence reconciliation}
An OCR result and a complainant statement are separate sources. If the two agree, the match can be surfaced for confirmation; if OCR supplies a value not mentioned in the narrative, it can fill a candidate field; if they disagree, the difference should remain visible for review. The repository's reconciliation module implements these distinct outcomes and generates missing-information gaps. This is preferable to silently overwriting one source with another, but it does not establish authenticity of an image or prove that a transaction occurred.\par\medskip
\section{Position of the project}
The contribution is an integrated prototype workflow that connects intake, classification support, evidence extraction, review, and local case persistence. It is not a new OCR engine, language model, or validated cybercrime risk model. Its engineering value is in connecting these components with explicit review steps and a separate investigator experience.\par\medskip

\item OCR, ASR, and LLM outputs are fallible; the interface should require human confirmation.

\section{Intake workflow}
\begin{enumerate}
\item A complainant starts a session and gives an incident description through text, voice-derived text, or the manual form.
\item The intake logic extracts known details and evaluates what important information is missing.
\item The assistant asks a follow-up question based on the current gap state. The draft and conversation are persisted in SQLite during the session.
\item If a relevant item is requested or available, the complainant uploads an image or PDF. The file is stored locally, and the OCR path returns extracted text and candidate fields.
\item The interface presents candidate OCR data for review. Reconciliation compares the fields to the complainant's description and marks agreement, OCR-only data, gaps, or conflicts.
\item The complainant corrects the transcript, extracted values, and narrative, then confirms the draft.
\item The application classifies the confirmed narrative as decision support and generates a structured case record and draft document.
\item The local investigator environment loads the submitted case, reviews the narrative and evidence, and updates its workflow status.
\end{enumerate}

\section{Evidence extraction and reconciliation}
OCR is performed through Tesseract for supported images; PDF pages are made available to the extraction path through PyMuPDF. Regular expressions and known-name lists identify candidate amount, UTR/RRN/transaction reference, phone number, date, time, UPI ID, email, masked ID, bank, payment app, or platform. Candidates carry a value and a heuristic confidence field. This confidence indicates extraction plausibility, not a calibrated probability that the OCR is correct.\par\medskip
The reconciliation module deliberately keeps typed and OCR sources separate. It reports:\par\medskip
\begin{itemize}
\item \textbf{Agreement:} the same relevant value appears in the typed account and evidence.
\item \textbf{OCR-only:} evidence contains a candidate value not stated in the narrative.
\item \textbf{Conflict:} the two sources differ, so the mismatch remains reviewable.
\item \textbf{Gap:} neither source currently supplies the requested information.
\end{itemize}
The application must not treat a candidate OCR value as verified transaction truth. The complainant or investigator should inspect the original file, especially for long numeric identifiers and low-quality images.\par\medskip

\section{Classification and urgency support}
The classifier loads \texttt{classifier.joblib}, \texttt{vectorizer.joblib}, and \texttt{label\_encoder.joblib} from \texttt{models/}. It transforms complaint narrative using the saved vectorizer and obtains LinearSVC decision scores. The system ranks labels and returns the top alternatives. A bounded function of the top-versus-runner-up margin is displayed as confidence-like information. It is not a calibrated probability and must be interpreted with the stated caveat. The category taxonomy includes 21 labels in the saved model artifacts.\par\medskip
The sentiment/urgency component identifies potential urgency cues, including an emergency or ``golden hour'' state. It is a prioritization aid and cannot determine whether a transfer can be reversed or guarantee a financial recovery. The legal mapping module provides suggested references for review, not a legal opinion or final section selection.\par\medskip
\section{Conversational and speech paths}
The conversational intake stores user/assistant messages and draft fields in SQLite. A configured Gemini or Ollama provider can support follow-up conversation or narrative standardization. Code includes deterministic fallback behavior when a provider is unavailable or output fails validation. A model response can still be incomplete or unsuitable; validation and visible draft correction remain necessary.\par\medskip
The interface supports browser speech recognition where available. An optional backend path transcribes uploaded audio with Whisper when installed and configured. Recognized words and especially amounts, names, dates, and transaction IDs should be corrected before submission. The application provides text entry so the user can correct voice transcription or proceed without audio.\par\medskip

\section{Investigator environment}
The investigator interface is designed as a separate operational view. It loads locally received cases, presents a queue and filters, opens a case detail view, and exposes complaint summary, complainant-provided fields, suspected identifiers, attached evidence, OCR/reconciliation results, suggested classification or legal information, and workflow actions. Imported case JSON is validated before it is saved. Workflow changes are written back into local case/index storage.\par\medskip
The investigator UI is only as complete as the case payload and local storage. Empty or incomplete records can exist, and imported records require validation. \section{Model evaluation and interpretation}
The repository README records 10,500 generated examples and 21 categories. The random split contains 7,350 training, 1,575 validation, and 1,575 test rows. A template-disjoint split contains 7,149 training, 1,680 validation, and 1,671 test rows, with 801 templates kept within a single split. The README reports a macro-F1 of 1.0000 on both split schemes, but it explicitly warns that categories have vocabulary exclusive by construction. Therefore:\par\medskip
\begin{enumerate}
\item The generated labels are lexically separable under the benchmark construction.
\item Real-world generalization and real incident accuracy have not been measured by this result.
\item The score should not be used as a claim of production accuracy or investigator reliability.
\item A hand-written, independently reviewed, privacy-safe gold set and external evaluation are required before making accuracy claims.
\end{enumerate}
The displayed margin-derived confidence is also not calibrated. A future evaluation should measure calibration and category-wise precision/recall on representative, consented, de-identified data, with a pre-registered evaluation protocol and clear human oversight.\par\medskip
\section{Strengths}
\begin{itemize}
\item The workflow combines narrative, manual entry, OCR candidates, and investigator review instead of treating classification as the whole product.
\item OCR identifiers are extracted with deterministic patterns and can be traced to evidence text.
\item The reconciliation design retains conflicts and separates evidence-only fields from the complainant's own description.
\item Draft editing and manual intake provide a correction path when voice or LLM output is wrong.
\item Local case persistence allows a submitted complaint to appear in an investigator queue without relying on a static demo list.
\item The repository documents the limitations of its synthetic classification benchmark rather than presenting that score as real-world accuracy.
\end{itemize}

\clearpage\chapter{Conclusion and Future Work}
\section{Conclusion}
The current project has expanded from a complaint classifier into a local cybercrime intake and investigator-review prototype. It connects conversational/manual reporting, voice-derived text, OCR-based candidate extraction, evidence reconciliation, category suggestions, draft generation, and local case storage. The separate investigator interface provides a path to review submitted records and update their workflow. The implementation's most important design principle is that OCR, ASR, and model output remain reviewable suggestions rather than verified facts.\par\medskip
The project is suitable for continued academic development and controlled demonstration. It is not an official complaint-filing service or production-ready case-management system. The synthetic classification benchmark does not establish real-world accuracy, and local storage does not supply production security controls. Those limits must remain explicit in demonstrations and documentation.\par\medskip
\section{Future work}
\begin{enumerate}
\item Improve the dataset using a legally and ethically approved, consented, de-identified process; establish a human-reviewed gold set and evaluate out of distribution.
\item Calibrate or remove margin-derived confidence and provide per-class error analysis.
\item Add source highlighting, confidence/provenance displays, and explicit confirmation for each OCR/ASR field.
\item Expand conversation regression tests to verify one meaningful question at a time, real-time field updates, no repeated answered questions, and OCR-aware gap suppression.
\item Add secure authentication, authorization, encryption at rest, configurable retention/deletion, immutable audit events, backup and recovery, and deployment threat modeling.
\item Align Streamlit and standalone frontend capabilities with a shared workflow checklist and cross-interface acceptance tests.
\item Improve accessibility, multilingual/code-switching support, keyboard navigation, and low-bandwidth behavior.
\item Validate statutory references against current official sources and keep them explicitly non-binding until qualified review.
\item Define an approved deployment and official-filing integration only with institutional and government authorization.
